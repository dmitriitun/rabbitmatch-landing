# Потребление ресурсов

Сервис `landing-backend` на Railway тарифицируется по гигабайто-минутам памяти.
В отчёте за период Aug 10 – Sep 10 он дал 16 105,87 GB-min ≈ **$3,73 из $3,75**
стоимости сервиса — то есть счёт за лендинг это практически целиком RAM,
удерживаемая всегда включённым контейнером (в среднем ≈ 370 МБ). CPU за тот же
период — 4,75 vCPU-min, $0,0022. Оптимизировать имело смысл только память.

## Что её ела

### 1. Полный каталог сообщений в HTML каждой страницы

`messages/ru.json` — 115 КБ, из которых **~100 КБ приходится на namespace
`legal`** (семь юридических документов). Он передавался в
`NextIntlClientProvider` целиком и, значит, инлайнился в RSC-payload **каждой**
страницы, хотя читает его только `/legal/[slug]`.

Теперь `pickClientMessages()` (`src/lib/messages.ts`) отдаёт браузеру только те
namespace, которые реально читают клиентские компоненты. Серверные компоненты
работают через `getTranslations` и видят полный каталог — не потеряно ничего.

### 2. Глубокое клонирование каталога на каждый рендер

`loadOverridesAndMerge` выполняла `JSON.parse(JSON.stringify(base))` над всем
каталогом **при каждом рендере**, включая заходы ботов и сканеров. Это был
главный источник короткоживущего мусора: V8 расширяет кучу под пиковую нагрузку
и не возвращает её ОС, а Railway тарифицирует именно резидентную память.

Теперь кэшируется **готовый merged-результат**, а не строки переопределений:
клонирование происходит максимум раз в TTL на локаль. Когда переопределений нет
(обычный случай) базовый объект отдаётся как есть, без клонирования вообще.

### 3. Динамический рендер каждой страницы

Локаль бралась из cookie, а сессия — из `getSession()` в layout. Любой вызов
`cookies()` в пути рендера отключает статику: каждый запрос — полный рендер
React-дерева.

Устранено с двух сторон:

- локаль пришла из URL-сегмента (`/en`, `/ru`), см. `docs/seo.md`;
- сессия резолвится **на клиенте**. Роут логина ставит рядом с httpOnly-cookie
  читаемую подсказку `rm_signed_in`, и только браузер с этой подсказкой тратит
  запрос на `/api/auth/me`. Анонимные посетители получают статический HTML и не
  делают ни одного auth-запроса.

Результат: все 20 контентных страниц (10 маршрутов × 2 локали) плюс 14
юридических помечены в сборке как **● SSG** — отдаются из пререндера.

### 4. Клиентский компонент на каждую строку текста

`EditableText` был клиентским компонентом, чтобы админ мог править текст на
месте. Значит, каждый заголовок, подпись и пункт списка открывал собственную
клиентскую границу — их сотни, и все они сериализуются в RSC-payload и
гидрируются в браузере ради функции, которой пользуются несколько
админ-сессий.

Теперь это **серверный** компонент: обычный HTML с атрибутом `data-rm-key`. Один
клиентский компонент `AdminEditLayer` перехватывает клики делегированием и
показывает редактор — но только когда обнаружена админская сессия. Публичный
посетитель не скачивает и не гидрирует ничего.

### 5. Полное дерево зависимостей в рантайме

`next start` держит в том же процессе, который тарифицируется, всё дерево
зависимостей репозитория. Включён `output: 'standalone'` — Next трассирует, что
реально импортируется, и собирает минимальный сервер:

```
node_modules полностью:            508 МБ
node_modules в standalone-выводе:   21 МБ
```

`nixpacks.toml` докладывает в вывод `public/` и `.next/static/` (Next этого не
делает, ожидая CDN), `railway.json` запускает `node .next/standalone/server.js`.

### 6. Мелочи

- Убраны `InteractiveDots` (canvas-анимация с requestAnimationFrame на каждый
  кадр), `ScrollReveal` (IntersectionObserver на каждой секции) и
  `AnimatedCounter`. Это клиентский CPU, но заодно — вся «нейрослоп»-эстетика.
- Один шрифт вместо двух (Onest с латиницей и кириллицей) — одна загрузка до
  первой отрисовки.
- `images.unoptimized: true`: оптимизатор Next держит буферы sharp в памяти и
  тянет за собой арену libvips на всё время жизни процесса. Оптимизировать
  нечего — скриншоты приложения собираются заранее (`npm run build:shots`) уже
  в WebP нужного размера, логотип тоже. Отдаём файлы как есть, sharp в рантайме
  не нужен вовсе.
- `/api/health` намеренно **не трогает Postgres**: healthcheck, падающий из-за
  временного сбоя БД, заставил бы Railway перезапускать контейнер, прекрасно
  способный отдавать статику.

## Что стоит выставить в Railway

```
NODE_OPTIONS=--max-old-space-size=320
```

V8 по умолчанию растит кучу под доступную память хоста и не спешит её отдавать.
Явный потолок заставляет собирать мусор раньше и удерживает резидентную память
около заданного значения. 320 МБ с запасом хватает для отдачи пререндеренных
страниц; если в логах появится OOM — поднимайте шагами по 64 МБ.

Дополнительно, если перед сервисом стоит Cloudflare (код rate-limit читает
`cf-connecting-ip`, так что, похоже, стоит): включите Cache Rule на кэширование
HTML для `/en/*` и `/ru/*`. Страницы статические, и тогда до контейнера будет
доходить лишь малая доля запросов.

## Как перемерить

```bash
npm run build
```

В таблице маршрутов `●` = SSG. Любая контентная страница, ставшая `ƒ`
(Dynamic), означает, что в путь рендера просочился вызов `cookies()`,
`headers()` или `searchParams` — это регрессия, и именно она вернёт счёт за
память обратно.
