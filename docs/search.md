# Поиск по сайту

Кнопка с лупой в шапке, `/` с клавиатуры — и поле, которое ищет по всему
сайту сразу. Поле фильтра внутри раздела Академии делает то же самое: сужает
дерево раздела и **под ним** показывает совпадения из остальной части сайта.

Две вещи, ради которых это устроено именно так:

1. **Результат ведёт на место, а не на страницу.** Ссылка несёт запрос в
   параметре `?rmq=`, и страница, на которую пришёл читатель, подсвечивает все
   вхождения и прокручивается к первому.
2. **Сначала то, что рядом.** Совпадения на текущей странице идут отдельной
   группой сверху. Человек, который ищет из статьи, обычно имеет в виду «в этой
   статье»; тот, кто нет, получает остальной сайт прямо под ней.

## Что попадает в индекс

Содержимое сайта лежит в трёх несвязанных местах, и читателю всё равно, в
каком из них ответ:

| Источник | Что берётся | Единица выдачи |
|---|---|---|
| `messages/<locale>.json` + `content_overrides` | Тексты страниц, написанных кодом | Группа ключей (`players.match`, `padel.faq`) |
| `page_layouts` | Всё, что собрано конструктором | Секция документа |
| `site_nodes` | Разделы и статьи Академии | Страница |
| `legal.*` | Юридические документы | Документ |

Служебные пространства имён — `nav`, `footer`, `login`, баннер cookie — в
индекс не идут. Они есть на каждой странице, поэтому совпадение в них есть
везде, а это то же самое, что совпадения нет нигде.

Скрытые узлы дерева и скрытые секции отфильтровываются **при сборке индекса**,
а не при запросе: фильтрация на втором пути — то, о чём забывают.

## Почему не полнотекстовый поиск Postgres

Половина корпуса — JSON-файл, а не таблица: индексировать в базе нечего. А
весь корпус — несколько сотен килобайт, и просканировать его дешевле, чем
сходить за результатом по сети. Индекс собирается в память, живёт по TTL
(`CONTENT_CACHE_TTL_MS`) и сбрасывается явно из конструктора, менеджера
разделов и правки текстов: админ, опубликовавший страницу, должен находить её
сразу, иначе поиск выглядит сломанным.

## Совпадение по словам

Стеммера нет — сравнение по префиксу, минимум четыре символа. Контент в
основном русский: «правило», «правила», «правилам» и «правилами» имеют общий
корень, до которого не доберётся никакая отрезалка английских окончаний, и
общий префикс, до которого доберётся эта. Правило работает в обе стороны,
поэтому запрос «правилами» находит «правило».

Ранжирование, по убыванию влияния:

- совпадение в заголовке блока весит заметно больше, чем в теле;
- найдены **все** слова запроса — сильный бонус, который делает многословный
  запрос похожим на поиск фразы, не будучи им;
- точное вхождение всей фразы — ещё бонус;
- повторы дают убывающую отдачу: слово десять раз — не десятикратный ответ, и
  вознаграждать это значило бы поднимать наверх текст, набитый ключевыми
  словами;
- текущая страница — плюс к весу, который гарантированно ставит её первой.

С одной страницы в выдачу попадает не больше двух блоков. Без ограничения
длинная страница с нужным словом в каждом разделе занимает весь список и
прячет шесть других страниц, которые отвечают на вопрос, — самый обычный
способ для поиска по небольшому сайту перестать быть полезным.

Ответ сообщает не только найденное, но и **какие слова запроса не встречаются
на сайте вообще**. «Ничего не нашлось» и «такого слова у нас нет» — разные
сообщения, и второе экономит человеку следующую попытку.

## Подсветка на странице

`SearchHighlight` читает `?rmq=`, обходит текстовые узлы внутри `<main>`,
оборачивает совпадения в `<mark data-rm-found>`, раскрывает `<details>` над
первым из них и прокручивает к нему.

Почему не якорь и не текстовый фрагмент: у фразы в середине четвёртого абзаца
якоря нет, а расставлять их на каждый абзац сайта ради поиска — большая правка
разметки ради маленькой возможности; `#:~:text=` поддержан не во всех
браузерах. Обход DOM находит слова там, где они оказались, и ни одному
источнику контента не нужно знать, что поиск существует.

Компонент обёрнут в `Suspense` в макете локали: он читает строку запроса, а без
границы это чтение вывело бы каждую страницу из статического рендера.

## API

| Метод | Путь | Кто |
|---|---|---|
| `GET` | `/api/search?q=&locale=&path=` | все |

Публичный: всё, что он может вернуть, и так доступно по клику. `path` —
подсказка для ранжирования, а не разрешение: неверный путь просто не даёт
бонуса. Ограничение частоты щедрое (90/мин), потому что живое поле шлёт запрос
на каждое нажатие клавиши после дебаунса.

## Файлы

| Файл | Что в нём |
|---|---|
| `src/lib/search/types.ts` | Формы ответа, токенизация, правило совпадения слов — без `server-only`, чтобы браузер мог их импортировать |
| `src/lib/search/index.ts` | Сборка индекса из трёх источников, ранжирование, сниппеты |
| `src/components/Search/SiteSearch.tsx` | Кнопка в шапке и оверлей |
| `src/components/Search/SearchResults.tsx` | Список результатов, общий для оверлея и фильтра раздела |
| `src/components/Search/useSiteSearch.ts` | Дебаунс и отбрасывание устаревших ответов |
| `src/components/Search/SearchHighlight.tsx` | Подсветка на странице приземления |

## Проверка

```bash
curl -s 'http://localhost:3000/api/search?q=подача%20снизу&locale=ru&path=/padel'
```

Ожидается: `matchedWords` содержит оба слова, первые попадания — с `/padel`
и `onThisPage: true`, в `snippet` части с `hit: true` покрывают найденные
формы слов целиком, а не только совпавший префикс.

Затем открыть `href` первого результата: на странице появляются `<mark>`, и
браузер прокручивается к первому.
